# 结果驱动的技术沟通：从听众任务到材料

## 先定义完成，而不是定义目录
在动笔前，写一条结果声明：
「这场会议结束后，主要听众〔角色/权限〕能够从〔当前认知/困境〕变为〔希望形成的准确判断〕，并在〔条件/边界〕下〔做适当行动或复述/迁移〕；用〔可观察信号〕检查；不把〔业务成效、审批、掌声等〕当作已实现。」
举例：风险变更会的成功不是一定拿到批准，而是负责人知道风险暴露、可选路径、恢复条件和自己要决定什么；深度分享成功不是所有人都说好，而是同行可预测一个变体的表现、知道何时不用该技术。

### 听众模型（只用实际信息；未知写假设）
| 维度 | 要理解的事情 | 如何影响材料 |
|---|---|---|
| 决策权限 authority | 批准、建议、使用、评审、知情？是否缺席真正决策者？ | 请求与权限匹配；无权限者不承诺 |
| prior_knowledge | 共同词汇、系统背景、经验及错误心智模型 | 决定从哪个层级开始、是否做术语桥 |
| stakes | 业务、稳定性、预算、交付、个人负担、评审标准 | 选择价值、冲突和证据尺度 |
| barrier | 不在意、不理解、不信、不能做、不愿做？ | 分别处理相关性、解释、证据、权限、成本 |
| evidence_threshold | 哪类证据足以支持何种决定？基线、对照、实验、生产数据、真实职级？ | 区分可观察事实、推断、建议与假设 |
| secondary_audience | 次要受众/分歧、他们的疑问如何进入下钻 | 主线服务主要听众，保护非专家；细节进入备注/附录 |
| basis | 来自用户、已有会议记录、实际反馈或待确认假设 | 不将画像当读心术，不假装领导已经支持 |

### 反推与验收
先设计结尾要听众说出/做出的具体动作，再设计中间他们必须跨越的认知阶梯，最后选择入口。outcome 中：
- recall：希望听众准确记住的一句话（含必要条件），而非口号。
- observable_signal/check_method：用行为或准确复述/选择/预测/练习观察；不把沉默、满意、掌声当赞成。
- next_step：谁在什么条件下做什么；知识分享可为尝试、判断或练习，不强制 CTA。
- success_boundary/non_goal：哪些结果并不由本次沟通保证；批准/实施/收益/晋升是不同事件。
- follow_up：会后如何核对真实结果、记录未决、负责人与拟定日期；未知就明确待确认。

## 有张力但不操纵
可用「真实痛点/反常现象→为什么当前理解不足→核心判断→证据与取舍→可操作收束」。开场先让听众知道为何值得听、会得到什么，紧急事件先直陈风险与请求，不先讲故事。技术分享可以用失败复现、直觉预测与反例打开问题，再揭示机制；领导汇报先给结论和选择，不埋到最后。任何悬念都必须兑现；不能为了惊喜隐藏风险、夸张危机或伪造案例。
- 先抓相关性，再建立理解；先给必要词汇和图例，再讲复杂因果。
- 技术深度不是术语数。解释输入、状态、边界、关键不变量/机制、为什么替代路径不行、如何验证和迁移。示例/类比须区分真实、合成和推断。
- 从活动到价值：任务 → 技术难题 → 关键判断/行动 → 可验证结果 → 因果/归因限制 → 组织影响/复用。没有证据时，保留成果的局限，不能倒推出虚假的个人贡献。
- 反例和替代不应只藏在附录：影响当场判断的限制可见；附录用于深挖而非隐瞒。

## 澄清问题的优先级
先判断哪个未知会改变核心结论、行动、授权或叙事选择。把其余信息写为可编辑假设。每轮给当前判断→为什么这一问重要→一个问题→可能选项/开放回答。典型顺序（按需要，不跑流程）：
1. 会议结束必须发生什么？谁可以决定？听众原来怎么看？
2. 最容易失败/被质疑的地方？真实约束、标准、基线、替代路径？
3. 你手里有哪些可公开核查的证据？贡献是谁的？结果是否已验证？
4. 目标受众的基础、时间及真实分歧？能否承诺动作？哪些内容不能对外？
缺口不改变结论则不问；仅缺数据可给验证方案。若用户已经提供答案，不复问。
